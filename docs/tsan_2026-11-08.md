## Findings

There are no reports to triage.  The following are not races but are what
a reader should know before trusting "clean".

### N1. The reactor's TSan edge is global, so it can hide races (recommendation)

`client/client/core/kqueue_reactor.cpp`: the kernel carries a knote's udata
from the `kevent` ADD on the publishing thread to the harvest on the reactor
thread, an edge neither C++ nor TSan sees.  The code makes it visible with
one global atomic, `g_reactor_tsan_helper`: every `_kevent` call (ADD *and*
DELETE, every frame) does `fetch_or(0, release)` first, and the reactor does
`load(acquire)` after each harvest.

Every modification of the helper is an RMW, so the release sequence headed
by any publisher's poke is unbroken, and the reactor's acquire load
synchronizes-with every poke that precedes the value it reads in the
helper's modification order -- not only the poke for the knote it is about
to dispatch.  Consequently TSan sees a happens-before edge from everything
any thread did before *any* earlier `_kevent` to every frame the reactor
schedules after a later harvest (and, through the pool, to whatever those
frames resume).  The real kernel edge is per-knote.  The over-approximation
can mask a race between, say, a coroutine that writes X then arms frame A,
and frame B's continuation that reads X, if B happens to be harvested after
A's poke and nothing else orders them.

Experiment (not committed): replacing the global helper with
`__tsan_release(this)` in `_kevent` and `__tsan_acquire((void*)event.udata)`
before `global_work_queue_schedule` -- the per-knote edge (01a0c08 had an
`__tsan_acquire(udata)` in the reactor, removed in 0e0557a) -- gave a clean
run (exp1) with the full suite complete.  So in this suite the global edge
is not hiding anything TSan could otherwise find, on one run's evidence.

Recommendation for Antony: either keep the global helper (portable, no
sanitizer interface dependency, one release RMW per kevent in every build)
and accept the documented blind spot, or adopt the per-udata annotation
under `__has_feature(thread_sanitizer)` so TSan's view matches the kernel's
edge.  Uncertain point: a receipt-0 DELETE returns no acquire on the
deleting side in either form; today nothing after a successful DELETE reads
frame state written before the ADD that is not otherwise ordered (the
Callback was registered via `std::stop_callback`, whose registration and
invocation libc++ orders, before the ADD), so I see no gap, but I have not
checked every `_delete_knote` caller beyond `Callback::operator()` and
`spawn`.

### N2. What TSan cannot certify here

- TSan only judges the interleavings that actually ran.  The relaxed-RMW
  plus acquire-garnish protocol in `CancelableKEventFrame` (`_state`
  fetch_or relaxed in `Callback` and `static_resume`, release in `spawn`,
  the acquire re-load on the winning path) is exactly the case where a rare
  interleaving matters; the model-checker item in todo.md is still the
  right tool for it.
- There are no `std::atomic_thread_fence` calls anywhere in `client/`, so
  the usual TSan false-positive class (fence-based protocols) does not
  arise; the epoch service's happens-before (garbage_collection.md 2.1) is
  built on acquire/release RMWs on one word, which TSan models directly.
- TSan intercepts GCD (`dispatch_async_f`) and fd read/write, so
  `TransferToBlockableExecutor` and the socket/pipe transports are modelled;
  Metal is not exercised by `--test-only` (headless).
