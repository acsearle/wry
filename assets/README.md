# wry/assets: text assets under version control

This folder holds the game's **text assets**: hand-editable data that would
otherwise be numbers and strings baked into the executable, kept here so git
can diff and review them. One JSON file per domain, each record keyed by the
save-format short name (`WATER`, `COAL`, `ADD`), never by numeric code, so
the files survive renumbering.

| File | What | Loaded by |
|---|---|---|
| `terrain.json` | display name and map tint (`color_srgb`) per terrain kind | `game/presentation.cpp`, at startup |
| `matter.json` | display name and pile colour per matter kind; `price_compiled_in` is a read-only reference | `game/presentation.cpp`, at startup |
| `opcodes.json` | DRAFT display name, one-line summary, help text and stack effect per opcode, for antony to edit | `game/presentation.cpp`, at startup; no UI shows it yet |

Colours are `"#rrggbb"` in sRGB. A `_comment` key in any
object is ignored.

## Presentation only, for now

Everything here is **presentation**: per-client, freely editable, never read
by the simulation. The simulation's tables (matter prices, dig times and
yields, terrain generator parameters) stay compiled in, because lockstep
multiplayer hashes the World every step and a joiner receives the World, not
the rules; a per-client rules file would desync at the first sale or dig.
See `docs/data_driven.md` for the two ways rules could move to data later
(a ruleset hash in HELLO, or rules in the World). `matter.json` carries
`price_compiled_in` so the file reads as a complete record, but editing it
changes nothing, and a unit test fails if it drifts from `MATTER_PRICE`.

## How the game finds these files

CMake lists `assets/*.json` as sources of the app bundle with
`MACOSX_PACKAGE_LOCATION Resources/data`, so every build copies them into
`client.app/Contents/Resources/data/`, and re-copies a file whenever it
changes. At startup (`core/main.mm`, before any other thread starts) the
game loads them from the bundle's `Resources/data`. If that directory is
absent (an Xcode build, which does not copy them) it falls back to this
folder in the source tree, found from the source file's own path.

So: **edit here, then rebuild** (the build only copies; nothing compiles).
A missing file or a missing key falls back to the compiled-in value with a
warning on stderr and in the floating log; an unknown key warns and is
ignored. A malformed file warns and leaves the compiled-in values in place.

## What stays in ~/Desktop/assets

`~/Desktop/assets` (outside git) keeps the **binary blobs and caches**:
meshes (`.obj`, `.blend`), textures and atlases (`.png`, `.jpg`), fonts,
sounds, the save databases, and anything regenerated from sources. The game
still `chdir`s there at startup (`core/main.mm`) and loads those by relative
path; `config/settings.json` (user settings) and `saves/` live there too.

## LATER: move the rest of the text over

The plan, not yet done: move the human-readable, git-diffable parts of
`~/Desktop/assets` into this repo -- `.json` data into `wry/assets/`, `.py`
generators (`tools/`, `noise/`, `terrain/`) and `.svg` sources into
`wry/assets/` or `wry/tools/` -- leaving `~/Desktop/assets` holding only
static and cached `.png`s, meshes, fonts and the like (perhaps, eventually,
nothing). Ambiguous cases stay where they are and get discussed first, for
example:

- `assets.json` and `assets.svg`: the tile-atlas source, but generated by
  `tools/make_assets.py`, and read at runtime by the game;
- `config/settings.json`: user-owned, written by the game, so not a repo file;
- `opcodes.json` in `~/Desktop/assets`: a 2023 list of opcode names, read by
  nothing (one commented-out line in `WryWorldScene.mm`); superseded by this
  folder's `opcodes.json`;
- `backup*/` folders: snapshots of generator scripts, which git history
  would replace.
